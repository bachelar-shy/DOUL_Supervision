# DOUL administrator-issued password login (staging/pilot)

This is an opt-in **local password identity** for existing project participants. It does not allow public signup, fabricate Party/RoleAssignment, or replace qualified personnel verification. The main domain authority model remains server-enforced.

1. Provision an approved site foundation (Project, Party, RoleAssignment, Qualification) using existing deployment procedures. No real users may log in to synthetic demo data.
2. Supply a matching RS256 private signing key and pinned public verification key as separate operator-owned, permission-restricted secret files; use the explicit `compose.operational.password.yml` overlay, `DOUL_AUTH_MODE=local-password` and `DOUL_AUTH_PRIVATE_KEY_FILE`. Build the Web image with `VITE_DOUL_AUTH_MODE=password` and verify `/health.adapters.authentication` before enabling login. The private key is never committed, exposed to the browser, or sent to users. Runtime refuses a mismatched key.
3. An operator creates **only the first** administrator's credential, with existing active ADM Party/RoleAssignment IDs, by running `python -m services.deployment.password_admin --username <id> --party-id <uuid> --role-id <uuid>` against an approved staging/pilot DB. The operator enters a password interactively, never on the command line. Appropriate `DATABASE_URL_FILE` and JWT verification/signing configuration must be supplied.
4. Subsequent accounts are generated by the administrator under **관리 > 사용자 계정 생성** from already provisioned participants. Account username is lowercase ASCII 3-64 characters (`a-z`, digits, `.`, `_`, `-`), password 12-128 characters. Passwords are salted scrypt hashes, never plaintext. The API uses one-time unique JWT identifiers, 15-minute access tokens and server-side revoked-token checks.
5. Existing installed `@doul/client` development role-selection stays limited to demo; operational Vite images must opt into `VITE_DOUL_AUTH_MODE=password` at build time; an external-mode build fails closed rather than exposing the development role picker.
6. Browser login uses `/auth/login` and logout uses `/auth/logout`. Both require the allowed HTTPS browser Origin. Five consecutive bad passwords lock the account for 15 minutes. Password login must be served behind HTTPS. An administrator must update/deactivate a role or Party through existing governed project administration; server checks those changes on **every** protected request.

**Limits:** Password reset/recovery, administrative account disable/reactivation and long-term session renewal are not included in this first implementation. Do not launch a real site until credential recovery, operational password distribution, browser/session acceptance, agreed security tests and the field pilot have been completed. Demo role switching remains isolated in development mode and is never an operational login.

**Session handling:** 15-minute token expiry produces a visible re-login prompt; an auth failure is never retried as an official write. Forms with unsaved local changes may be lost on expiry and the UI warns accordingly. Failed network sign-out clears local credentials but shows that server revocation could not be confirmed.
